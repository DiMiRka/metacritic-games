# Игры Metacritic

Сервис раз в час забирает 20 игр с Metacritic, которые сегодня ещё не обрабатывались, и для каждой:

- сохраняет оценки Metascore и игроков по платформам и историю их изменений
- пишет нейросетью резюме отзывов критиков и игроков (что нравится и что нет) и переводит описание на русский
- находит самый популярный летсплей на YouTube и делает заключение по речи блогера
- подбирает похожие игры по эмбеддингам описаний

Веб-интерфейс: каталог с поиском, фильтром по платформе и сортировкой (по умолчанию по Metascore), карточка игры.\
Служебная часть (мониторинг воркера, очередь задач и кнопка ручного запуска) доступна только администраторам после входа.

Стек: Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 16 + pgvector + pg_trgm, Jinja2 + HTMX, APScheduler, Claude или любой OpenAI-совместимый LLM (по умолчанию в примере Gemini), fastembed, yt-dlp и faster-whisper, Docker Compose, Caddy, Prometheus и Alertmanager.

Сутки для обхода, расписание и ночная очистка считаются по `TIMEZONE` (по умолчанию московское время).\
Время в интерфейсе показывается в часовом поясе браузера: сервер отдаёт момент в UTC, а `app/web/static/time.js` переводит его в пояс пользователя.

## Запуск в Docker

В `docker-compose.yml` весь стек: `db`, `migrate` (миграции и роли базы при каждом старте), `web`, `worker`, `worker-letsplay`, `caddy` (HTTPS), `backup`, `prometheus`, `alertmanager` и по профилю `offsite` `backup-offsite`

### Локально

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
docker compose exec web python -m app users create-admin admin
```

Шаблоны, статика и код лежат в образе, поэтому после правок образ нужно пересобрать:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build web
```

Флаг `-f docker-compose.dev.yml` передавайте всегда. Без него compose пересоздаст `db` без порта `5432`, и тесты с локальным uvicorn перестанут видеть базу.

### В проде

Хватит 2 vCPU и 4 ГБ памяти. IP сервера должен быть **не российским**: API Gemini и Claude не обслуживают российские адреса, YouTube оттуда тоже работает плохо. Домен не обязателен: адрес вида `203-0-113-10.sslip.io` сам указывает на IP `203.0.113.10`, и Caddy получит на него настоящий сертификат Let's Encrypt. Наружу открываются только порты 80 и 443 у Caddy, Postgres, Prometheus и Alertmanager наружу не публикуются.

Желательно задать и остальное, что описано в `.env.example`: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` для тревог, `DEADMAN_PING_URL`, внешние бэкапы, при желании `SENTRY_DSN`

**2. Запуск.** Образы собирает CI и публикует в GitHub Container Registry: `ghcr.io/dimirka/metacritic-games-web`, `-worker` и `-offsite`, теги `latest` и SHA коммита. На сервере ничего не собирается:

```bash

docker compose up -d

```

Если пакеты в GHCR приватные, сначала один раз `docker login ghcr.io` (логин GitHub и токен с правом `read:packages`). Чтобы закрепить версию, укажите `IMAGE_TAG=<sha коммита>` вместо `latest`. Первый проход стартует сразу после запуска воркера (`CRAWL_ON_START`), дальше раз в час

**3. Администратор**

```bash
docker compose run --rm web python -m app users create-admin admin
```

Пароль (не короче 12 символов) вводится интерактивно и нигде не хранится в открытом виде.\
Сменить пароль: `python -m app users set-password admin`, все сессии пользователя при этом завершаются

**4. Второй фактор.** Не обязателен, но для администратора в проде рекомендуется:

```bash
docker compose run --rm web python -m app users totp admin
```

Команда покажет ключ и ссылку `otpauth://`. Ключ нужно добавить в приложение-аутентификатор (Google Authenticator, Aegis, 1Password) и ввести код из него: второй фактор включается, только если код подошёл. При входе код спрашивается на отдельной странице после пароля. Выключить: `python -m app users totp-off admin`. Чтобы администратор без TOTP вообще не мог войти, задайте `ADMIN_TOTP_REQUIRED=true`.

Сразу после включения команда выводит 10 резервных кодов вида `abcd-efgh-ijkl`. Они нужны на случай потери телефона: каждый вводится на странице кода вместо кода из приложения и действует один раз. Коды показываются только однажды, сохраните их вне сервера. Новый набор выдаёт `python -m app users recovery-codes admin`, прежние при этом перестают действовать.

### Бэкапы

Сервис `backup` (`scripts/backup.sh`) каждый день в `BACKUP_HOUR` по `TIMEZONE` делает `pg_dump -Fc` в том `backups`. Сразу после дампа он восстанавливает копию в отдельную базу `restore_check` и сверяет версию схемы с рабочей базой. Только после этого бэкап считается успешным.

- Итог каждого запуска пишется в таблицу `backup_runs`. Монитор и метрики берут из неё возраст последнего проверенного бэкапа
- Тревоги `BackupStale` (нет проверенного бэкапа больше 26 часов) и `BackupFailed` приходят в тот же Telegram
- Копии старше `BACKUP_KEEP_DAYS` удаляются
- Если успешного бэкапа нет больше суток, например после первого запуска, копия делается сразу, не дожидаясь назначенного часа

**Внешнее хранилище.** Профиль `offsite` поднимает контейнер с rclone и [age](https://age-encryption.org). Раз в час он шифрует новые дампы и докладывает их в любое S3-совместимое хранилище (AWS S3, Backblaze B2, Яндекс Object Storage, Selectel).

В дампе лежат хеши паролей и сессий, поэтому без шифрования копии не выгружаются вообще. Шифрование открытым ключом: на сервере есть только открытый ключ получателя, закрытый хранится у вас. Даже взломанный сервер не расшифрует то, что уже ушло в хранилище, а утечка из хранилища ничего не даёт без закрытого ключа

Ключ создаётся на своей машине, не на сервере:

```bash
age-keygen -o metacritic-backup-key.txt    # закрытый ключ: в менеджер паролей или на флешку
grep 'public key' metacritic-backup-key.txt # открытый ключ age1...: в BACKUP_AGE_RECIPIENTS
```

Можно указать несколько открытых ключей через запятую, например второй у запасного администратора.\
Остальные настройки задаются переменными `RCLONE_CONFIG_OFFSITE_*` и `BACKUP_REMOTE` в `.env`:

```bash
docker compose --profile offsite up -d
```

Ключи хранилища получает только этот контейнер. Срок хранения во внешнем хранилище задаётся правилом жизненного цикла бакета

**Восстановление** из последней копии:

```bash
docker compose stop web worker
docker compose exec backup sh -c 'pg_restore --clean --if-exists --no-owner -d "$PGDATABASE" "$(ls -t /backups/*.dump | head -1)"'
docker compose run --rm migrate      # права ролей и функции
docker compose start web worker
```

Копию из внешнего хранилища сначала нужно расшифровать закрытым ключом на своей машине: `age -d -i metacritic-backup-key.txt metacritic-….dump.age > restore.dump`. Затем положить её в том `backups` и восстановить так же. Секреты TOTP в дампе зашифрованы ключом из `SECRET_KEY`, поэтому для восстановления на новом сервере нужен и тот же `SECRET_KEY`. Без него администраторам придётся заново включить второй фактор.

## Структура проекта

Код разложен по предметным областям: всё про одну часть системы лежит в одном пакете

```
app/
  core/         настройки, подключение к базе, базовая модель, время, проверка внешних URL,
                роли базы с минимальными правами
  catalog/      игры: модели, запросы каталога, похожие игры, схемы JSON API
  scraper/      клиент Metacritic (лимит запросов, повторы) и разбор ответов
  youtube/      поиск летсплея, субтитры и распознавание речи Whisper
  jobs/         очередь задач в Postgres: выборка с арендой, повторы, пулы исполнителей,
                LISTEN, circuit breaker (ничего не знает о Metacritic и LLM)
  enrichment/   LLM-резюме отзывов и эмбеддинги
  crawler/      этапы обхода как задачи (collect, scrape_game, summarize, embed),
                курсор дня, учёт проходов в run_items, правила автоматов
  monitoring/   снимок состояния для /monitor
  auth/         пользователи, пароли, серверные сессии, команды для пользователей
  web/          FastAPI: routes/ (публичные, служебные, вход), middleware/ (CSRF,
                заголовки, лимиты), шаблоны и статика
  worker/       процесс воркера: пулы по видам задач, расписание, сборщик аренд, heartbeat
  cli.py        команды python -m app
tests/          повторяют структуру app/, фикстуры ответов Metacritic в tests/fixtures
migrations/     Alembic
monitoring/     Prometheus: опрос и правила тревог, запуск Alertmanager с Telegram
scripts/        бэкап базы с проверкой восстановления
```

Веб-приложение собирает фабрика `create_app(settings)` в `app/web/app.py`. Пул соединений создаётся в `lifespan` и закрывается вместе с приложением. Настройки, шаблоны и база лежат в `app.state`, обработчики берут их оттуда через зависимости, поэтому тест может собрать приложение со своими настройками. Воркер и команды CLI получают базу через `default_database()` при первом обращении, при импорте модулей соединения не создаются. Настройки, переданные в фабрику, действуют по всему пути запроса: в cookie, CSRF и шифровании секретов TOTP, в лимитах попыток входа, задержке и сроках сессии, в лимитах частоты (их счётчики тоже свои у каждого приложения), в мониторе, логах и Sentry. Функции `app/auth/service.py`, `app/auth/crypto.py`, монитора и `app/core/db_roles.py` получают настройки параметром.

Общий объект `settings` читают только точки сборки: `create_app()` без аргументов (так его вызывает uvicorn), воркер и команды CLI. Тест `tests/web/test_settings_injection.py` запрещает импорт `settings` в модулях пути запроса. Там же собирается приложение со своими настройками и проверяется, что действуют именно они.

Зависимости идут в одну сторону: `web` и `worker` → предметные пакеты → `core`. `core` ни от кого не зависит, `web` никто не импортирует. Правила записаны в `tests/test_architecture.py`, новый импорт против них уронит тесты.

Команды:

```bash
python -m app worker                       # воркер по расписанию
python -m app crawl                        # один проход сейчас (живому воркеру или в этом процессе)
python -m app users create-admin <login>   # администратор, пароль через getpass
python -m app users set-password <login>   # смена пароля, сессии пользователя завершаются
python -m app users totp <login>           # включить второй фактор TOTP
python -m app users totp-off <login>       # выключить его, сессии пользователя завершаются
python -m app users recovery-codes <login> # новые резервные коды, прежние перестают действовать
python -m app users rekey                  # перешифровать секреты TOTP текущим SECRET_KEY
python -m app db-roles                     # роли app_web и app_worker (делает сервис migrate)
python -m app reparse [--slug <slug>]      # пересобрать игры из сохранённых сырых ответов
python -m app refresh                      # в очередь устаревшие резюме и эмбеддинги
python -m app cleanup                      # очистка старых данных сейчас, не дожидаясь ночи
uvicorn app.web.app:create_app --factory   # сайт
```

## Обход и очередь задач

Вся фоновая работа идёт через таблицу `jobs` в Postgres.\
Celery, Redis и прочие брокеры не нужны, а очередь тестируется на той же фикстуре базы

```
расписание (раз в час) ─┐
POST /api/v1/runs ──────┴─► collect ─► scrape_game ×20 ─┬─► summarize (critic, user)
                                                         └─► embed
```

- **collect** под advisory lock набирает до 20 игр, которые сегодня ещё не брались, и ставит по задаче `scrape_game` на игру. Курсор дня тот же: New Releases, затем страницы browse
- **scrape_game** скачивает карточку, оценки и отзывы. Если сырой ответ тот же, что в прошлый раз, игра не перезаписывается. Иначе сохраняет игру, отзывы (`game_reviews`), сырой ответ и изменившиеся оценки. В обоих случаях сверяет резюме и эмбеддинг и ставит `summarize` и `embed`, только если они устарели
- **summarize** и **embed** читают данные из базы и пересчитывают резюме и вектор
- **letsplay** находит самый популярный летсплей игры на YouTube, переводит речь блогера в текст и делает по нему заключение (раздел «Летсплеи»)

Как работает очередь:

- **Выборка** одним `UPDATE … FOR UPDATE SKIP LOCKED`, сама работа идёт вне транзакции. Задачу держит аренда (`locked_until`), долгие задачи продлевают её в фоне. Если воркер упал, сборщик раз в минуту вернёт задачу в очередь
- **Повторы.** Сеть, таймауты, 429 и 5xx повторяются с экспоненциальной паузой. «Игры нет», ошибка формата, отказ модели и прочие 4xx сразу получают статус `dead`. Dead-задачу можно повторить кнопкой в мониторе
- **Отсрочка.** Если работа невозможна до известного момента (исчерпана суточная квота), обработчик поднимает `DeferredError(until)`: задача возвращается в очередь с `run_after = until`, попытка не тратится и строка в `run_items` не пишется
- **Дедупликация** через `dedupe_key`: одна и та же работа не попадёт в очередь дважды, пока прошлая не завершилась. Второй `collect` создать нельзя, поэтому `POST /api/v1/runs` отвечает 409
- **Параллельность по видам**: у Metacritic, LLM и эмбеддингов свои лимиты (`SCRAPE_CONCURRENCY`, `SUMMARY_CONCURRENCY`, `EMBED_CONCURRENCY`). Медленный этап не тормозит остальные. У летсплеев свой лимит `LETSPLAY_CONCURRENCY=1`: Whisper занимает процессор
- **NOTIFY** на канале `jobs` только будит воркеры. Пропущенное уведомление подхватит опрос раз в `JOB_POLL_SECONDS`, сама задача уже лежит в таблице
- **Проход** закрывается в транзакции завершения последней своей задачи: `success`, `partial` (часть этапов сдалась) или `failed` (упал сам сбор). Каждая попытка каждого этапа пишет строку в `run_items`, из них монитор считает счётчики и показывает ошибки
- **Circuit breaker.** Автоматы `metacritic` и `llm` хранятся в таблице `breakers`. После серии сбоев (ошибки формата или 5xx и 429 у Metacritic, неверный ключ, кончившаяся квота или серия 429 у LLM) задачи этого сервиса откладываются без траты попыток. Потом одна пробная задача проверяет, ожил ли сервис. Сбой LLM не мешает сохранять игры и считать эмбеддинги. В мониторе панель «Внешние сервисы» показывает все автоматы человеческими словами: «работает» (закрыт) с временем последней выполненной задачи, «приостановлен до …» (открыт) с причиной из последнего сбоя (`breakers.last_error`) или «ждёт пробную задачу», если пауза уже закончилась
- **Остановка.** По SIGTERM воркер перестаёт брать задачи, ждёт текущие до `WORKER_SHUTDOWN_GRACE_SECONDS` и возвращает недоделанные в очередь без траты попытки. В compose у воркера `stop_grace_period: 45s`
- **Экземпляры.** У каждого свой heartbeat со списком задач, которые он держит. Имя экземпляра — `WORKER_ID` или `пулы@hostname:pid`, например `letsplay@14e5b4ae2b44:1`. По пулам монитор подписывает экземпляр («Основной воркер», «Воркер летсплеев») и показывает по каждой роли только живые экземпляры, а если живых нет — последний замолчавший. Записи контейнеров прошлых сборок прячутся, штатно остановленные удаляются при старте воркера, остальные через сутки

**Ограничение.** Лимит частоты запросов к Metacritic (1 в секунду) работает внутри процесса. Если запустить два процесса воркера, обрабатывающих `scrape_game`, частота удвоится. Поэтому `scrape_game` обрабатывает один процесс. По той же причине `python -m app crawl` при живом воркере только ставит ему `collect` и ждёт конца прохода, а свой обработчик поднимает, лишь когда живых воркеров нет. Остальные виды задач можно масштабировать отдельными экземплярами. Общий лимитер через базу следующий шаг, если понадобится горизонтальное масштабирование

## Летсплеи

Для каждой игры воркер находит самый популярный летсплей на YouTube, переводит рассказ блоггера в текст, делает по тексту заключение и показывает его на странице игры со ссылкой на ролик\
Работа разбита на две задачи очереди:

| Задача | Где выполняется | Автомат | Что делает |
|---|---|---|---|
| `letsplay` | `worker-letsplay` | `youtube` | ищет ролик, переводит речь в текст и сразу сохраняет расшифровку (статус `transcribed`), в той же транзакции ставит `letsplay_conclude` |
| `letsplay_conclude` | основной `worker`, пул `summarize` | `llm` | пишет заключение по сохранённой расшифровке |

Если LLM упала, повторяется только заключение: звук не скачивается, Whisper заново не запускается. Когда у LLM кончается квота, заключения ждут вместе с резюме отзывов, а расшифровки продолжают копиться

Обе задачи идут вне прохода. Проход закрывается, когда сохранены игры, резюме и эмбеддинги, и не ждёт Whisper. Остановленный `worker-letsplay` тоже не держит проход открытым. Ошибки летсплеев видны в мониторе среди dead-задач и в `letsplays.error`.

Летсплей ищется **только для игр с Metascore**, и очередь разбирается по убыванию оценки: приоритет задачи равен лучшему Metascore игры. Квоты API хватает примерно на 100 поисков в сутки, а обход приносит до 480 игр. У нишевых новинок без оценок летсплеев обычно нет, и поиск по ним тратил бы квоту на «не найдено». Игра без оценки получит летсплей, когда у неё появится Metascore.

Задача `letsplay` ставится после сохранения игры с Metascore в трёх случаях: летсплея ещё нет, прошлая попытка не удалась больше суток назад или с последнего поиска прошло `LETSPLAY_REFRESH_DAYS` (30 дней). Если самым популярным остался тот же уже расшифрованный ролик, обновляются только просмотры, а `letsplay_conclude` пересчитывает заключение, только если сменились промпт (`LETSPLAY_PROMPT_VERSION`) или модель.

1. **Поиск.** Запрос «<название игры> let's play».
   - Поиск идёт только через YouTube Data API: `search` по релевантности и `videos` за просмотрами и длительностью. Ключ `YOUTUBE_API_KEY` обязателен. Без него пул `letsplay` не запускается, и воркер пишет об этом при старте.
   - Ключ передаётся заголовком `X-Goog-Api-Key`, а не в адресе: адрес запроса попадает в текст ошибок, а оттуда в журналы, монитор и Sentry.
   - Из 25 найденных роликов отбираются подходящие. В названии должны быть все значимые слова названия игры, длительность не меньше `LETSPLAY_MIN_DURATION_MINUTES`, ролик не должен быть про другую игру, как «Hades в Minecraft», и не должен иметь ограничение 18+ (`contentRating.ytRating` в ответе API): без входа в аккаунт YouTube не отдаёт у таких роликов ни субтитры, ни звук. Подходящие сортируются так: сначала ролики с признаками прохождения в названии (let's play, walkthrough, part 1, #1), внутри по просмотрам.
   - Если в самом популярном ролике нет речи (прохождение без комментариев, нет ни субтитров, ни голоса в начале) или ролик недоступен, берётся следующий. Всего пробуется до `LETSPLAY_MAX_CANDIDATES` (3) роликов. Каждая неудачная попытка это Whisper на начале ролика, около 10–20 секунд. Блокировка YouTube и сбои сети перебор прерывают: их разбирают повтор и автомат.
2. **Речь в текст.** Здесь работает yt-dlp, и только здесь. Официальный API текст и звук чужих роликов не отдаёт: `captions.list` показывает, какие субтитры есть, но `captions.download` отвечает 401, он доступен только владельцу ролика через OAuth. Сначала берутся субтитры на языке ролика: ручные, иначе автоматические, которые YouTube распознал из той же речи. Переводы не берутся. При автодубляже YouTube у ролика десятки дорожек на разных языках, и берётся исходная.

   Если субтитров нет, речь распознаёт [faster-whisper](https://github.com/SYSTRAN/faster-whisper):
   - модель `small` в int8 на CPU, с фильтром тишины;
   - неуверенные куски, повторы и выдуманные фразы вроде «Thanks for watching» отбрасываются;
   - распознаются только первые `LETSPLAY_MAX_AUDIO_MINUTES` (20) минут исходной звуковой дорожки. Скачивается только это начало, запросом с Range и без ffmpeg.
3. **Заключение.** Расшифровка уходит в ту же LLM, что пишет резюме отзывов, внутри тега `<transcript>` как данные. В ответ приходят 3–5 предложений по-русски и вердикт `positive`, `mixed` или `negative`.

На странице игры появляется блок «Мнение летсплейщика»:

- заключение и вердикт;
- ссылка на ролик, только на `www.youtube.com`, канал, просмотры и длительность;
- пометка, сделано ли заключение по субтитрам или по распознанной речи.

В `GET /api/v1/games/{slug}` те же поля лежат в `letsplay`. Расшифровка хранится в базе, но через API не отдаётся.

**Отдельный сервис `worker-letsplay`.** Это тот же образ воркера с `WORKER_POOLS=letsplay` и `WORKER_SCHEDULE=false`, у него свои лимиты: `cpus: 1.5`, `mem_limit: 2g`. Whisper занимает весь выданный CPU. В общем процессе он тормозил бы обход Metacritic, продление аренд задач и heartbeat. Основной воркер запущен с `WORKER_POOLS=metacritic,summarize,embed` и только ставит задачи `letsplay`. Ключи разнесены по сервисам: ключ YouTube и cookies есть только у `worker-letsplay`, ключи LLM — только у основного воркера.

**Квота API.** У YouTube Data API 10 000 единиц в сутки, это около 100 поисков: один поиск стоит 100 единиц на `search` и 1 на `videos`. Когда квота кончается, воркер запоминает время её сброса (полночь по тихоокеанскому времени) и до него API не вызывает. `QuotaExceededError` — это отсрочка (`DeferredError`): задача возвращается в очередь до момента сброса без траты попытки, а автомат `youtube` открывается тоже до сброса, а не на полчаса, так что пробных задач до этого момента нет. После сброса поиск идёт как обычно. Запоминание живёт в памяти процесса, так что перезапуск стоит одного лишнего запроса.

**Ошибки и автомат `youtube`**

| Ошибка | Что происходит |
|---|---|
| Ролик недоступен, в нём нет речи, у него ограничение 18+ | Берётся следующий кандидат. Если кандидаты кончились, задача сразу `dead` |
| Сеть, 429 и 5xx | Задача повторяется |
| Проверка «не бот ли вы» | Автомат `youtube` открывается сразу и откладывает летсплеи, не тратя попыток |
| Ключ API не принят (`keyInvalid`, `accessNotConfigured`, `forbidden`, ключ ограничен другим IP) | Автомат `youtube` открывается сразу: такую ошибку исправляет только человек, и без автомата каждая игра по очереди получила бы `failed` |
| Квота API исчерпана | Задача и автомат `youtube` ждут сброса квоты, попытки не тратятся |

Открытый автомат виден в мониторе, тревога `CircuitBreakerOpen` приходит через 15 минут.

**yt-dlp устаревает быстро.** Он отвечает только за субтитры и звук, но YouTube регулярно ломает его старые версии.

- Workflow `.github/workflows/yt-dlp.yml` каждый день обновляет в `uv.lock` только yt-dlp и открывает пул-реквест. Еженедельный Dependabot yt-dlp пропускает. Пул-реквест от `GITHUB_TOKEN` не запускает CI. Чтобы проверки шли сами, нужен секрет `DEPS_PR_TOKEN`: fine-grained токен с правами contents и pull requests.
- Тревога `LetsplayTranscriptsStalled` срабатывает, если за 12 часов задачи летсплеев падали или повторялись не меньше 5 раз, а ни одной расшифровки не было.

**Cookies аккаунта Google.** Если YouTube требует подтвердить, что запрос не от бота, помогают cookies аккаунта. Файл cookies — это полный доступ к аккаунту, поэтому:

1. Заведите **отдельный пустой аккаунт** только для этого, не личный и не рабочий. YouTube может заблокировать его за автоматизированные запросы, и терять его не жалко.
2. Выгрузите cookies в формате Netscape из **приватного окна** браузера: войдите в этот аккаунт на youtube.com, выгрузите cookies расширением «Get cookies.txt LOCALLY» и сразу закройте окно, не выходя из аккаунта. Если продолжать пользоваться той же сессией в браузере, YouTube быстро обновит cookies, и выгруженные перестанут действовать.
3. Положите файл на сервер в `secrets/youtube-cookies.txt` и дайте прочитать его только пользователю контейнера (uid проверяется командой `docker compose exec worker-letsplay id -u`, обычно 1000): `chown 1000:1000 secrets/youtube-cookies.txt && chmod 600 secrets/youtube-cookies.txt`. В git и в образ файл не попадает.
4. Смонтируйте его только для чтения: раскомментируйте строку `volumes` у `worker-letsplay` в `docker-compose.yml` (`./secrets/youtube-cookies.txt:/run/secrets/youtube-cookies.txt:ro`), укажите `YOUTUBE_COOKIES_FILE=/run/secrets/youtube-cookies.txt` в `.env` и выполните `docker compose up -d worker-letsplay`.

Файл видит только `worker-letsplay`. yt-dlp при закрытии записывает обновлённые cookies обратно, поэтому воркер при старте копирует файл во временную папку `/tmp` и работает с копией: смонтированный исходник остаётся только для чтения. Cookies со временем истекают: если снова появились проверки «не бот ли вы», выгрузите их заново и перезапустите `worker-letsplay`.

**Ограничения:**

- Для ремастера часто находится летсплей оригинала: слова «Remastered» и «Edition» в названии ролика не требуются.
- По Whisper заключение отражает только первые 20 минут. Субтитры обычно покрывают весь ролик.
- При смене самого популярного ролика старое заключение снимается со страницы, пока не готово новое.

**Проверено на живом YouTube** (`tests/contract/test_youtube_live.py` и прогон в Docker на пяти играх). Самые популярные летсплеи нашлись, речь взята из субтитров, заключения получились осмысленными. Whisper в контейнере распознал минуту речи за 28 секунд.

## Данные

**Сырые ответы.** Ответы Metacritic по игре (карточка, оценки игроков по платформам, отзывы) хранятся в `raw_pages` сжатыми zlib, с sha256 канонического JSON. Из карточки берутся только блоки, которые читает парсер: цены и новости на странице меняются при каждом запросе, с ними hash не совпадал бы никогда. Одинаковый ответ новой строки не создаёт, только обновляет `last_seen_at`. После правки парсера `python -m app reparse` пересобирает игры из последних сырых ответов без единого запроса к Metacritic.

**История оценок.** `score_history` (игра, платформа, metascore, userscore, время) пишется только при изменении оценок, поэтому растёт медленно. Отдаётся через `GET /api/v1/games/{slug}/scores`, годится для графика и сортировки «в тренде».

**Резюме.** В `review_summaries` хранятся hash набора отзывов, модель, `prompt_version` и токены ответа LLM (`input_tokens`, `output_tokens`). Резюме пересчитывается, если поменялось что-то из первых трёх. Константа `PROMPT_VERSION` в `app/enrichment/llm.py` увеличивается при каждой правке промпта или схемы ответа. Монитор показывает токены за сутки и, если заданы `LLM_PRICE_INPUT_PER_MTOK` и `LLM_PRICE_OUTPUT_PER_MTOK`, примерную стоимость.

**Перевод описаний.** Описание игры с Metacritic переводит на русский та же LLM, что пишет резюме отзывов. Это задача `translate` в пуле `summarize` под автоматом `llm`.

- Перевод лежит в `games.description_ru`, оригинал остаётся в `games.description`: по нему считаются эмбеддинги и похожие игры.
- Перевод пересчитывается, только если поменялось описание, модель или промпт (`TRANSLATE_PROMPT_VERSION`). Для этого рядом хранится ключ `description_ru_key` — sha256 от всех трёх.
- Если описание сменилось, пока шёл запрос к LLM, устаревший перевод не сохраняется.
- Модель получает описание внутри тега `<description>` как данные: названия игр, студий и персонажей просит не переводить, ничего не добавлять и не сокращать.

На странице игры показывается перевод, а под ним раскрывается «Оригинал с Metacritic». Лёгкие модели иногда ошибаются: gemini-3.5-flash-lite перевёл «assassins» как «ассистенты» и имя героя Soul как «Соул». Поэтому оригинал всегда под рукой. На коротких описаниях лёгкие модели ещё и возвращают английский текст без изменений. Тогда в той же задаче уходит второй запрос с прямым указанием, что текст не русский, и только если не помог и он, попытка считается неудачной. Пока перевода нет, показывается оригинал. В API у игры два поля, `description` и `description_ru`. Для уже сохранённых игр переводы ставит `python -m app refresh` или следующий обход.

**Эмбеддинги.** У игры хранятся `embedding_model` и `embedding_hash` (sha256 текста, из которого считан вектор). Тот же текст той же моделью не пересчитывается. Похожие игры ищутся только среди векторов той же модели. После смены модели или `PROMPT_VERSION` `python -m app refresh` ставит в очередь всё устаревшее. Без этой команды устаревшее подтянется само при следующем обходе каждой игры.

**Статусы** во всех таблицах проверяются CHECK-ограничениями, которые строятся из `StrEnum` в коде (`enum_check` в `app/core/models.py`). Список значений задаётся в одном месте. Нативный `ENUM` Postgres не взят: из него нельзя удалить или переименовать значение без пересоздания типа.

**Хранение.** Каждую ночь в `CLEANUP_HOUR` воркер удаляет пачками завершённые задачи, проходы с их `run_items` и курсоры старше `RETENTION_DAYS` (30 дней). Также удаляются старые версии сырых ответов старше `RAW_RETENTION_DAYS` (90 дней), но последний ответ по каждой игре остаётся всегда, иначе reparse будет не из чего делать. Каталог, резюме и история оценок не чистятся. Секционирование по месяцам не понадобилось: при 20 играх в час это десятки тысяч строк в месяц, удаление пачками с этим справляется. Секции станут нужны, если объём вырастет на порядки.

## API

JSON API версионирован: `/api/v1/...`. Документация в dev открывается на `/docs`, в проде выключена.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/v1/games` | каталог с поиском, фильтром по платформе, сортировкой и страницами |
| `GET /api/v1/games/{slug}` | карточка игры, резюме отзывов и похожие игры |
| `GET /api/v1/games/{slug}/scores` | история оценок по платформам |
| `GET /api/v1/monitor` | снимок мониторинга, только администраторам |
| `POST /api/v1/runs` | ручной запуск прохода, только администраторам |
| `POST /api/v1/jobs/{id}/retry` | повтор dead-задачи, только администраторам |

Старые адреса без версии (`/api/games` и другие) отвечают `308` на тот же путь под `/api/v1` с заголовком `Deprecation: true`. Метод и тело запроса при таком перенаправлении сохраняются.

## Наблюдаемость

**Логи.** Логи пишутся через loguru. В контейнерах формат JSON (`LOG_FORMAT=json`), каждая строка — один объект: `ts`, `level`, `logger`, `msg` и поля контекста. Контекст хранится в contextvars и не протекает между задачами:

- задача воркера: `job_id`, `kind`, `run_id`, `slug` или `game_id`;
- сбор кандидатов: `run_id` с момента создания прохода;
- запрос к сайту: `request_id`, он же уходит в заголовке `X-Request-ID`.

`request_id` ставит Caddy (`{http.request.uuid}`) и передаёт приложению в `X-Request-ID`. Присланный клиентом заголовок Caddy заменяет своим. Журнал Caddy тоже в JSON и содержит поле `request_id`, поэтому одним значением находится запрос и в журнале прокси, и в журнале приложения:

```bash
docker compose logs --no-log-prefix caddy web | jq 'select(.request_id == "0f8fad5b-…")'
```

Если приложение запущено без Caddy, id генерирует оно само. Контекст держит ASGI-middleware (`app/web/middleware/request_id.py`), а не `BaseHTTPMiddleware`. Поэтому `request_id` есть и в строках, которые пишутся во время потокового ответа, например в потоке SSE монитора.

Стандартный `logging` (uvicorn, SQLAlchemy, APScheduler) перехватывается и идёт тем же путём. Все строки одного прохода находятся одним фильтром:

```bash
docker compose logs worker --no-log-prefix | jq 'select(.run_id == 12)'
```

Локально формат `text`: время, уровень, источник, сообщение и поля контекста в конце строки.

**Метрики Prometheus.** Источников два.

Счётчики процесса воркера отдаются на порту `9100`, он открыт только во внутренней сети `backend`:

| Метрика | Что показывает |
|---|---|
| `metacritic_requests_total{status}` | запросы к Metacritic по кодам ответа, включая повторы (`status="429"`, `"error"` при сетевом сбое) |
| `metacritic_request_duration_seconds` | время ответа Metacritic |
| `llm_request_duration_seconds{model,outcome}` | задержка запросов к LLM, отдельно удачные и с ошибкой |
| `llm_tokens_total{model,direction}` | токены на входе и выходе |
| `jobs_finished_total{kind,status}`, `job_duration_seconds{kind}` | итоги и время задач |

Показатели из базы общие для всех экземпляров. Их отдаёт web с отдельного порта `9101` и обновляет фоновой задачей раз в 15 секунд:

| Метрика | Что показывает |
|---|---|
| `jobs_queue{kind,status}` | длина очереди: queued, running, dead |
| `crawler_last_run_duration_seconds` | длительность последнего прохода |
| `crawler_current_run_seconds` | длительность текущего прохода |
| `crawler_last_success_age_seconds` | возраст последнего успешного прохода |
| `crawler_worker_heartbeat_age_seconds` | возраст последнего heartbeat любого воркера |
| `crawler_items_last_hour{status}`, `crawler_error_ratio_last_hour` | итоги этапов за час и доля сдавшихся |
| `breaker_open{name}` | открыт ли автомат |

Prometheus опрашивает порты `9100` (worker) и `9101` (web). Они открыты только во внутренней сети `backend`, Caddy проксирует лишь порт сайта `8000`.

Те же показатели web видны в браузере на `/metrics`, но только администратору после входа, как и монитор. В меню ссылки на них нет, адрес открывается напрямую. Аноним получает перенаправление на вход (или `401` для API), пользователь без прав — `403`. Адрес клиента роли не играет: частный IP из VPN или локальной сети доступа не даёт.

**Тревоги.** Prometheus и Alertmanager входят в `docker-compose.yml`. Правила лежат в `monitoring/alerts.yml`:

| Тревога | Условие |
|---|---|
| `WorkerHeartbeatStale` | heartbeat старше 2 минут, в том числе после штатной остановки |
| `NoSuccessfulRun` | нет успешного прохода больше 2 часов |
| `HighErrorRate` | больше 20% этапов за час сдались (при хотя бы 10 этапах), держится 10 минут |
| `MetacriticRateLimited` | больше 5 ответов 429 за 30 минут |
| `CircuitBreakerOpen` | автомат открыт дольше 15 минут |
| `TargetDown` | Prometheus не может опросить web или worker 2 минуты |

Порог доли ошибок меняется прямо в `monitoring/alerts.yml`.

**Сторожевой сигнал.** Prometheus и Alertmanager живут на том же сервере. Если упадёт сервер целиком, тревога о нём не придёт. Для этого есть правило `Watchdog`: оно горит всегда, и Alertmanager раз в минуту отправляет его на `DEADMAN_PING_URL` внешнего сервиса. Внешний сервис сам поднимает тревогу, когда пинги перестают приходить, то есть когда не работает сервер, Prometheus, Alertmanager или выход в интернет.

Настройка на healthchecks.io (бесплатного тарифа хватает):

1. Создать проверку с периодом 5 минут и запасом 5 минут.
2. Уведомления проверки направить в Telegram, на почту или в другой канал. Это должен быть канал, который не зависит от этого сервера.
3. Вписать адрес пинга `https://hc-ping.com/<uuid>` в `DEADMAN_PING_URL` в `.env` и перезапустить Alertmanager: `docker compose up -d alertmanager`.

Подойдёт любой сервис, принимающий HTTP-пинги: Dead Man's Snitch, Cronitor, Better Stack. `Watchdog` уходит только на этот адрес и в Telegram не попадает. Адрес пинга получает только Alertmanager.

Чтобы тревоги приходили в Telegram:

1. Создать бота у @BotFather.
2. Написать боту или добавить его в группу.
3. Взять id чата из `https://api.telegram.org/bot<токен>/getUpdates` (поле `chat.id`).
4. Вписать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env`.

Токен получает только Alertmanager: конфиг собирается при его старте (`monitoring/alertmanager-entrypoint.sh`), в репозитории токена нет. Без токена тревоги видны только в интерфейсе Alertmanager.

Интерфейсы Prometheus и Alertmanager опубликованы только на `127.0.0.1` сервера. С рабочей машины к ним можно подключиться через SSH-туннель:

```bash
ssh -L 9090:localhost:9090 -L 9093:localhost:9093 root@IP_СЕРВЕРА
```

После этого они открываются на `http://localhost:9090` и `http://localhost:9093`.

**Исключения.** При заданном `SENTRY_DSN` web и worker отправляют события в Sentry или совместимый сервис (GlitchTip, self-hosted Sentry):

- web — необработанные исключения запросов;
- web и worker — любые строки лога уровня ERROR, в том числе `logger.exception` и задачи, ушедшие в `dead`.

Поля контекста (`run_id`, `job_id`, `slug`, `request_id`) становятся тегами события. Персональные данные не отправляются (`send_default_pii=False`). Трассировка выключена, её включает `SENTRY_TRACES_SAMPLE_RATE`.

## Безопасность

**Сессии и CSRF.** Сессия запроса только читает базу. Отметку активности (`last_seen_at`, не чаще раза в минуту) пишет фоновая задача после отправки ответа, в своей транзакции. CSRF-токен — это HMAC-SHA256 от токена сессии на серверном `SECRET_KEY`: без секрета токен не подобрать, даже зная cookie. `SECRET_KEY` есть только у web и обязателен для него при `ENV=prod`: без ключа `create_app` не запустит сайт. `migrate` и воркеры загружают те же настройки с `ENV=prod` без ключа, он им не нужен, а любая попытка зашифровать или подписать что-то пустым ключом падает с понятной ошибкой. В dev без ключа берётся случайный на время жизни процесса.

**Вход и сессии.** Пароли хешируются argon2. Сессии хранятся на сервере (в базе только sha256 от токена), поэтому их можно отозвать: выход, смена пароля и деактивация пользователя действуют сразу. Cookie `HttpOnly`, `SameSite=Lax`, в проде `Secure` и префикс `__Host-`. У сессии два срока: абсолютный `SESSION_TTL_HOURS` (12 часов) и бездействие `SESSION_IDLE_MINUTES` (60 минут без запросов). Активность отмечается не чаще раза в минуту, это и есть точность таймаута. Открытая вкладка монитора сама сессию не продлевает: поток SSE только проверяет её, и через час без действий монитор предложит войти заново. Ответ и время проверки одинаковые для неверного логина и неверного пароля. Поток мониторинга перепроверяет сессию каждые 30 секунд и закрывается, если её отозвали.

**Подбор пароля.** Счётчиков два, оба в базе, а не в памяти процесса:

- **По паре IP и логин.** После `LOGIN_MAX_ATTEMPTS` неудач за `LOGIN_WINDOW_MINUTES` вход с этого адреса под этим логином закрыт до конца окна.
- **По логину с любых адресов.** Защищает от ботнета. После `LOGIN_DELAY_AFTER` неудач каждая следующая попытка ждёт 2, 4, 8… секунд, не больше `LOGIN_DELAY_MAX_SECONDS`. Это задержка, а не блокировка: сколько бы попыток ни делал атакующий, через ограничение админ не теряет доступ, а подбор замедляется примерно до одной попытки в минуту. Попытки, отклонённые из-за задержки, не записываются и не растягивают её. Задержка действует и для несуществующих логинов, так что по ней нельзя узнать, есть ли логин.

На каждой `LOGIN_ALERT_THRESHOLD`-й неудаче подряд в журнал web пишется предупреждение (логин, число попыток, число адресов). Монитор показывает логины с неудачными входами за сутки.

**Второй фактор.** TOTP по RFC 6238 реализован в `app/auth/totp.py` без сторонних библиотек. Один и тот же код второй раз не принимается: последний использованный шаг хранится в `users.totp_last_step`, а проверка и запись идут одним `UPDATE` с условием. Второй фактор включается и выключается для каждого администратора командами `users totp` и `users totp-off`, в том числе в prod. Без TOTP администратор входит по логину и паролю, без страницы кода. Если задать `ADMIN_TOTP_REQUIRED=true`, администратор без TOTP после верного пароля получит 403 с командой для включения.

**Вход в два шага.** Код спрашивается только у администраторов и отдельным шагом после пароля, viewer входит по паролю. Верный пароль администратора не создаёт сессию: в `login_challenges` появляется одноразовое ожидание кода (в базе только sha256 токена), токен уходит в cookie `__Host-login-code` (HttpOnly, Secure, SameSite=Strict), и браузер переходит на `/login/code`. Там принимается код TOTP или резервный код. На ввод даётся `LOGIN_CODE_TTL_SECONDS` (5 минут) и не больше `LOGIN_CODE_MAX_ATTEMPTS` (5) неверных кодов, потом ожидание удаляется и нужен пароль заново. Новый вход того же пользователя заменяет прежнее ожидание. Каждый неверный код записывается как неудачная попытка входа, поэтому задержка по логину и блокировка по IP действуют и на втором шаге. Исчерпанные попытки кода пишутся в журнал как `ERROR`: пароль был верным, значит, вероятно, он известен постороннему. Сброс попыток, `last_login_at` и замена старой сессии происходят только после второго шага. Просроченные ожидания удаляет `cleanup` вместе с сессиями.

**Секреты TOTP зашифрованы** AES-256-GCM (`app/auth/crypto.py`). Ключ выводится из `SECRET_KEY` через HKDF, поэтому в базе, в бэкапах и во внешнем хранилище лежит только шифротекст. В проверку целостности входит id пользователя: шифротекст одного пользователя не подойдёт другому. Резервные коды хранятся как хеши argon2.

**Смена `SECRET_KEY`:**

1. Новый ключ записать в `SECRET_KEY`, прежний — в `SECRET_KEY_PREVIOUS`.
2. Выполнить `docker compose up -d web`. При старте web перешифрует все секреты TOTP новым ключом и напишет в журнал, сколько перешифровал. Открытые страницы со старыми CSRF-токенами продолжают работать.
3. Очистить `SECRET_KEY_PREVIOUS` и ещё раз перезапустить web.

Если секрет не расшифровывается ни одним ключом, web пишет ошибку в журнал. Такому администратору нужно заново включить второй фактор командой `users totp`. После обновления с версии, где секреты хранились открытым текстом, web зашифрует их при первом старте сам.

**CSRF.** Все `POST`, `PUT`, `PATCH`, `DELETE` принимаются, только если `Origin` (или `Referer`) совпадает с адресом сайта. Для запросов от вошедшего пользователя дополнительно нужен заголовок `X-CSRF-Token`: токен выводится из токена сессии, лежит в `<meta>` и отправляется из `fetch` и htmx. На `SameSite=Lax` как на единственную защиту не полагаемся.

**CORS не включён намеренно.** Без CORS-middleware браузер разрешает чужим сайтам читать ответы API только того же источника. Сервису не нужны запросы с других доменов, поэтому любое ослабление этой политики только расширило бы поверхность атаки.

**CSP и заголовки.** Политику ставит middleware приложения: скрипты и стили только с собственного адреса (htmx лежит в `app/web/static`, инлайнового кода нет), картинки ещё с `www.metacritic.com`, iframe только с `cdn.jwplayer.com`, `frame-ancestors 'none'`. Плюс `nosniff`, `Referrer-Policy`, `Permissions-Policy`. HSTS ставит Caddy и только при `ENV=prod`. Ссылки из внешних данных (обложки, видео, летсплеи) проходят `safe_url`: только `https` и хост из списка разрешённых, а шаблоны проверяют их ещё раз перед выводом.

**Ограничение частоты.** `/`, `/api/v1/games` и `/login` ограничены по IP (`RATE_LIMIT_*`). Счётчики живут в памяти процесса web: при нескольких процессах uvicorn лимит фактически умножится на их число. Сейчас процесс один, это допустимо. Для нескольких процессов счётчик нужно вынести в Redis или в базу, как это уже сделано для попыток входа.

**Адрес клиента.** uvicorn запущен с `--forwarded-allow-ips "*"` и берёт IP из `X-Forwarded-For`. Это безопасно, потому что до web можно достучаться только из Caddy: web публикует порт только во внутреннюю сеть `frontend`, где кроме него есть один Caddy. Caddy же перезаписывает `X-Forwarded-For` реальным адресом клиента, так что подставить чужой IP снаружи нельзя.

**Роли в базе.** Владелец схемы используется только сервисом `migrate`. `app_worker` может читать и менять рабочие таблицы каталога и обхода и видит только `users.id` (чтобы записать, кто запустил проход). `app_web` только читает каталог, проходы, статусы и очередь, а пишет лишь в `users`, `sessions` и `login_attempts`. DDL ни у одной роли нет. Для таблиц будущих миграций заданы `ALTER DEFAULT PRIVILEGES`: воркеру рабочие права, сайту только чтение.

**Очередь для сайта закрыта на запись.** Сайт не может ни вставить, ни поменять, ни удалить строку в `jobs`. Ему доступен `SELECT` и `EXECUTE` на две функции `SECURITY DEFINER`, их создаёт `db-roles`:

- `request_manual_collect(user_id)` ставит только ручной `collect` и только от активного администратора. Пауза между ручными запусками проверяется внутри функции, так что через взломанный web её не обойти. `JOB_MAX_ATTEMPTS` и `MANUAL_RUN_COOLDOWN_MINUTES` подставляются в текст функции при `db-roles`.
- `retry_dead_job(id)` возвращает в очередь только задачу в статусе `dead`.

Обе функции работают с фиксированным `search_path`, `EXECUTE` у `PUBLIC` отозван. Тем же способом воркер чистит просроченные сессии и старые попытки входа функцией `purge_auth_records()`, не имея прав на сами таблицы.

**Переменные окружения.** Общего `env_file` нет. `.env` служит только для подстановки `${...}`, а каждый сервис получает явный список своих переменных:

- **worker:** ключи LLM и YouTube есть только у него.
- **migrate:** пароли ролей `app_web` и `app_worker` есть только у него.
- **web:** пароль своей роли в `DATABASE_URL` и настройки входа, лимитов и монитора.

Тест `tests/test_compose.py` следит, чтобы ключи не попали в web и чтобы каждая настройка из `Settings` доходила хотя бы до одного сервиса. Так новую настройку нельзя забыть.

**Готовность.** `/health` выполняет `SELECT 1` с таймаутом 3 секунды и отвечает 503, если база недоступна. По нему работает healthcheck web, а Caddy стартует только после `service_healthy` у web. Healthcheck воркера смотрит на файл, который воркер обновляет после каждого удачного heartbeat в базу (раз в 15 секунд). Если файл старше минуты, значит цикл воркера завис или база недоступна. Docker сам не перезапускает контейнер в статусе unhealthy, но статус виден в `docker compose ps` и в системе мониторинга хоста.

**Контейнеры и сети.** `backend` (db, web, worker) и `frontend` (web, caddy) внутренние, без выхода наружу. Выход в интернет есть только у воркера (Metacritic, LLM, YouTube) и Caddy (сертификаты). У web, worker и migrate файловая система только для чтения (кроме `/tmp` и тома с моделями), сброшены все capabilities и включён `no-new-privileges`. Caddy оставлена только `NET_BIND_SERVICE`. У всех сервисов есть лимиты памяти, у воркера с запасом под faster-whisper.

## Сборка и CI

**Образы.** `Dockerfile` собирает два образа. Зависимости в них ставятся по `uv.lock` с проверкой хешей (`--require-hashes`):

- `--target web`: сайт, API, миграции и команды пользователей, без fastembed, onnxruntime и LLM-клиентов;
- `--target worker`: обход, LLM, эмбеддинги и расписание, без FastAPI и Jinja.

Тесты `tests/web/test_factory.py` следят, чтобы импорт приложения web не тянул библиотеки воркера и наоборот.

**CI** (`.github/workflows/ci.yml`):

| Задание | Что делает |
|---|---|
| `test` | ruff, миграции вверх-вниз-вверх, `alembic check`, роли базы, pytest |
| `e2e` | Playwright с Chromium |
| `audit` | `pip-audit` по всему `uv.lock` |
| `images` | сборка обоих образов и проверка Trivy (падает на HIGH и CRITICAL с готовым исправлением), на `master` публикация в GHCR |
| `contract` | раз в неделю и вручную: контракт с живым API Metacritic |

Dependabot (`.github/dependabot.yml`) раз в неделю предлагает обновления `uv.lock`, базовых образов, образов в compose и GitHub Actions.

**Закреплённые образы.** Все внешние образы в `Dockerfile`, `docker-compose.yml` и CI указаны с точной версией и digest, например `caddy:2.11.9@sha256:…` и `pgvector/pgvector:0.8.7-pg16@sha256:…`. `docker compose pull` не подменит Postgres на другую минорную версию, а Caddy — на другую ветку 2.x без коммита в репозитории. Обновления приходят пул-реквестами Dependabot, где видно, что именно меняется. Тест `tests/test_compose.py` не даёт добавить образ без версии и digest и следит, чтобы Postgres в CI совпадал с compose: Dependabot не обновляет образы сервисов в workflow, их правят вместе с compose.
